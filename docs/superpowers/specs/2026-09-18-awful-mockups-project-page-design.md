# Awful Mockups Project Page Design

## Goal

Publish a real `/work/awful-mockups/` project page for the existing Awful Mockups project using the site's current entity-page architecture. The page presents a curated subset of the current 2D/PSD phone and laptop mockups, keeps all screen content neutral, and prepares a non-functional future download CTA without exposing the source files yet.

## Source material and scope

- Canonical mockup source set: `F:\\AWFUL_ASSETS\\Photoshop\\Mockups\\AWFUL-Mockups-2026-09-17\\PSD`.
- The current set contains 37 PSD files. The public project page must not display the full set.
- The page must show a curated selection of approximately 6–10 strong previews with variety across phone/laptop, portrait/landscape composition, light/dark/neutral/color backgrounds, and camera angle.
- Awful Mockups remains separate from Awful 3D Mockups. No Blender/GLB/3D device models belong on this page.
- Source PSD files are not downloadable in the first release.

## Screen-content rule

Every public preview must contain no unapproved UI, artwork, screenshots, or temporary imagery inside device screens.

Where a PSD contains `SCREEN CONTENT`, that layer is disabled for the public export. The visible screen should use the document's existing neutral `SCREEN SURFACE`, fill, mask, or another physically plausible empty-screen treatment. Do not bake temporary graphics into the previews merely to make the screen look occupied.

## Page architecture

Add `project:awful-mockups` to the existing typed entity-page pipeline rather than introducing a custom standalone page system.

The page should contain:

1. A normal project intro describing the PSD mockup set and its intended use for interface, identity, and graphic presentation.
2. A curated static media section using existing media-figure/media-group/mockup primitives.
3. One animated showcase using the existing Moves Awful animated-canvas-gallery runtime with only the curated Awful Mockups preview assets as inputs.
4. A download/resources section with a visibly disabled or unavailable `Скачать мокапы` action and a clear `Скоро` state. The initial implementation must not use `href="#"`, a fake URL, or a downloadable attribute.
5. Existing project navigation/shell behavior, responsive layout, caption system, analytics boundaries, and motion/reduced-motion contracts remain authoritative.

## Motion direction

Reuse the existing Moves Awful canvas gallery rather than the full `moves-canvas-demo` browser shell. The page is advertising the mockups, not the animation library.

Preferred initial gallery variant: `showcase-diagonal`; `arc` is an acceptable fallback only if visual QA shows materially better composition with the selected previews. Motion must respect the site's existing reduced-motion behavior and must not require a new animation dependency.

## Download contract

The first release prepares the future download surface but exposes no files.

The CTA must be rendered as non-interactive/disabled UI with `Скоро` messaging. When a storage target is chosen later (for example Yandex Disk), enabling download should require only supplying the real external resource URL/metadata through the existing content/resource-link boundary, not restructuring the page.

## Content and visual tone

Use the existing Awful Mockups name. Copy should explain that these are structured PSD mockups with editable scene layers, screen masks/surfaces, object treatment, background choices, and post-processing, without claiming that every source file is final or currently downloadable.

Green is allowed as one visual treatment but must not dominate the entire selection. The curation should deliberately mix neutral, light, dark, and selected color treatments.

## Catalog and discovery state

- Add a real route at `/work/awful-mockups/`.
- Register the page content and shell presentation through existing registries.
- Give the existing useful-project definition a real `href`.
- Change the Awful Mockups useful-project state from `coming-soon` to `live` only when the route, media, and smoke tests pass.
- Keep the page direct-link-only/unlisted/noindex initially, matching other developing project pages unless a separate discovery decision is made.

## Media integration

Public previews are derived exports, not raw PSDs. Store only web-ready preview assets in the site's media pipeline.

Each selected preview must have:
- a stable media asset id;
- a stable media entry id;
- accurate dimensions;
- concise alt text describing the physical scene/device, not invented screen content;
- project ownership associated with `awful-mockups`;
- responsive derivatives generated by the existing media tooling.

Do not add duplicate copies outside the canonical media system.

## Testing and acceptance

Implementation follows TDD for route/content contracts before production code.

Minimum acceptance:
- `/work/awful-mockups/` builds and renders through the entity-page renderer;
- page registries and ids validate;
- useful-project card links to the real page and is `live` only after page readiness;
- all selected images load through the media catalog and responsive pipeline;
- no preview contains unapproved screen UI/artwork;
- no raw PSD is publicly exposed;
- future download CTA is visible but cannot trigger navigation/download;
- Moves Awful showcase initializes with only Awful Mockups preview entries;
- reduced-motion behavior remains valid;
- desktop and mobile visual QA show no clipping, overlap, unreadable copy, broken controls, or dominant all-green treatment;
- existing core, project-page, media, local-link, typecheck, build, and smoke checks remain green.

## Non-goals

- Publishing every PSD.
- Publishing Awful 3D Mockups.
- Choosing the final download host.
- Adding new animation libraries.
- Rebuilding the site's general button/design system as part of this page.
- Putting temporary UI or artwork into device screens.
