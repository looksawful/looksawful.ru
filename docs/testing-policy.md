# Политика жизненного цикла тестов и проверок

Статус: нормативный документ репозитория.

Эта политика определяет, какие проверки создаются, где запускаются, сколько живут и когда должны быть удалены. Цель — сохранять надёжность сайта без накопления исторических тестов и без превращения обычной разработки или CMS-правок в длинный CI.

## 1. Основной принцип

Тест, созданный для разработки конкретного изменения, по умолчанию **временный**.

RED → GREEN подтверждает исправление на этапе разработки, но само по себе **не является причиной хранить тест постоянно**.

Постоянная проверка допустима только тогда, когда она защищает долгоживущий контракт или повторяющийся риск и является самым дешёвым надёжным способом его контролировать.

Новый `*.test.mjs` не должен автоматически становиться частью `test:fast`.

## 2. Классы проверок

### TEMPORARY

Одноразовая проверка для текущего бага, миграции, рефакторинга, эксперимента или воспроизведения browser quirk.

Жизненный цикл:

1. создать или адаптировать проверку;
2. получить ожидаемый RED, если это полезно для задачи;
3. реализовать изменение;
4. получить GREEN;
5. подтвердить результат подходящим интеграционным/production gate;
6. удалить проверку до завершения задачи, если она не прошла критерии постоянного теста.

TEMPORARY не входит в постоянный `test:fast`.

### CONTRACT

Постоянная дешёвая проверка долгоживущего инварианта системы.

Примеры:

- CMS не может менять code-owned route/ID;
- production публикует exact SHA;
- media registry не принимает неизвестные identity;
- parser fail-closed при нарушении стабильной структуры.

CONTRACT может входить в `test:fast`, если он действительно дешёвый и критичный.

### AFFECTED

Постоянная специализированная проверка подсистемы, которая запускается только когда затронута эта подсистема.

Примеры:

- navigation browser checks только для navigation/shared-runtime изменений;
- CV checks для CV изменений;
- media browser/integrity checks для media изменений.

AFFECTED не должен запускаться на каждое несвязанное изменение.

### PRODUCTION SMOKE

Маленький постоянный набор критической работоспособности опубликованного сайта.

Он проверяет только основные пользовательские гарантии: загрузку главной, JS/CSS/runtime sanity, навигацию, один репрезентативный проект, CV и базовую media sanity.

PRODUCTION SMOKE не должен превращаться в архив всех когда-либо исправленных UI-багов.

### FULL / QUALITY

Тяжёлые, широкие или медленные проверки: full E2E, Lighthouse, external links, расширенная media/browser regression, dependency/security quality gates.

Они выполняются вручную, по расписанию или для действительно широких изменений. Обычный push не является основанием для FULL / QUALITY.

## 3. Критерии постоянного теста

Перед тем как оставить новый тест постоянным, агент обязан ответить **да** на все вопросы:

1. Защищает ли тест правило, которое останется актуальным через месяцы, а не историю конкретной реализации?
2. Может ли этот дефект реалистично вернуться при обычных будущих изменениях?
3. Не покрывает ли риск уже существующий typecheck, build, contract, affected check или production smoke?
4. Проверяет ли тест наблюдаемое поведение/контракт, а не конкретную внутреннюю реализацию, старый literal copy или детали уже законченной миграции?
5. Достаточно ли тест дешёвый и стабильный для уровня, на котором предлагается его запускать?

Если хотя бы один ответ `нет`, тест должен быть `TEMPORARY` либо перенесён в `AFFECTED` / `FULL / QUALITY`.

## 4. Обязательный lifecycle каждой разработки

Перед завершением задачи все новые и изменённые проверки проходят отдельную классификацию:

`new tests → KEEP / MOVE / DELETE → удалить TEMPORARY → финальные gates`

Значения:

- `KEEP` — остаётся постоянный CONTRACT и указана причина;
- `MOVE` — остаётся, но только в AFFECTED/FULL/QUALITY;
- `DELETE` — временная разработческая проверка удаляется.

Финальный отчёт агента для задачи, в которой создавались или менялись тесты, обязан содержать:

- `NEW PERMANENT TESTS: N`
- `TEMPORARY TESTS REMOVED: N`
- `MOVED TO AFFECTED/FULL: N`

Если новый постоянный тест оставлен, агент кратко указывает защищаемый контракт.

## 5. Regression tests

Название `regression test` не даёт тесту права на бессрочное существование.

Разовый баг браузера, закончившаяся миграция, восстановление старого компонента или одноразовая трансформация данных могут использовать RED → GREEN тест во время работы и удалить его после успешного интеграционного/production подтверждения.

Постоянным regression test становится только тогда, когда он прошёл все критерии раздела 3.

## 6. Правила `test:fast`

`test:fast` — это **явно выбранный маленький набор постоянных дешёвых контрактов**.

Запрещено определять `test:fast` как «все `*.test.mjs`, кроме нескольких исключений».

Новый тест не входит в `test:fast`, пока его явно не добавили в fast-manifest/allowlist и не обосновали как CONTRACT.

`test:unit` может оставаться более широким дешёвым набором для локального/manual/scheduled контроля. Наличие теста в `test:unit` не означает, что он должен выполняться на каждом push.

## 7. Что должно оставаться постоянным

Нельзя удалять ради скорости проверки, которые защищают критические живые риски:

- exact production SHA и post-deploy verification;
- production build/typecheck;
- компактный production smoke;
- CMS authorization и запрет на code-owned поля;
- deterministic media fingerprint/cache integrity;
- media source/derivative integrity там, где media реально изменяются;
- основные route/page/domain identity contracts;
- security checks в их выделенном schedule/PR контуре.

Сокращение CI достигается маршрутизацией и удалением исторического мусора, а не отключением fail-closed гарантий.

## 8. Контент и CMS

Обычная правка authored text не должна запускать проверки компонентов, media, browser runtime или full build, если структурный контракт не изменился.

Тесты authored copy не должны фиксировать конкретные фразы, если сами фразы разрешено редактировать через CMS. Они могут проверять тип, структуру, identity, escaping, композицию и code-owned ограничения.

## 9. Изменение существующих тестов

При работе в уже существующем наборе сначала определить, что именно тест защищает.

- Если это живой CONTRACT — сохранить или упростить без потери гарантии.
- Если это специализированный риск — перенести в AFFECTED/FULL.
- Если это literal старого текста, завершённая migration fixture или история одноразового бага — удалить либо исключить из постоянного CI.
- Массовое удаление без классификации запрещено.

## 10. Принцип стоимости

Для каждой гарантии используется самый дешёвый достаточный уровень:

`static/typecheck → unit/contract → affected → production smoke → full/quality`

Не запускать более дорогой уровень, если более дешёвый уже надёжно доказывает требуемое свойство.

Политика считается частью архитектуры репозитория. Изменение этой политики требует отдельного осознанного решения, а не побочного изменения во время feature/hotfix работы.

## 11. Изменения CI и workflow

Изменения `.github/workflows/**`, CI routing, concurrency и test manifests считаются общим инфраструктурным контрактом и не должны разрабатываться несколькими независимыми fix-ветками одновременно.

Перед такой правкой обязательно:

1. проверить актуальный `dev` и открытые PR, которые меняют те же workflow/test-manifest файлы;
2. выбрать одну каноническую ветку для текущего CI-контракта; новая ветка либо продолжает её, либо явно supersede/закрывает предыдущую;
3. не держать одновременно два взаимоисключающих PR, исправляющих один и тот же CI-инвариант;
4. непосредственно перед merge повторно сравнить ветку с текущим `dev`; если релевантные файлы изменились, синхронизировать ветку и повторить финальные gates;
5. для изменения поведения workflow использовать RED → GREEN контракт, если риск можно дешёво выразить автоматическим тестом;
6. release PR из `dev` в `prod` не считать готовым, пока открыта незавершённая CI-fix ветка, меняющая его обязательные проверки или release semantics.

Цель правила — не запрет параллельной работы, а один источник истины для каждого CI-инварианта. Параллельные feature-ветки допустимы, параллельные взаимоисключающие определения одной и той же проверки — нет.

## 12. Необязательный responsive/UI слой

Адаптивные browser checks, которым нужен реальный layout engine, но которые слишком дороги для обычного `test:fast`, живут отдельным ручным слоем.

Канонический локальный запуск:

`npm run test:ui:responsive`

Канонический GitHub Actions workflow:

`UI Responsive` → `workflow_dispatch`.

Правила слоя:

- не запускать автоматически на обычные push/PR;
- использовать небольшой набор репрезентативных viewport, а не полный device zoo;
- начинать с Chromium, если конкретная задача не требует другого browser engine;
- проверять наблюдаемую геометрию и поведение: overflow, sticky/fixed placement, resize/reflow, основные responsive invariants;
- дешёвые статические/contract assertions оставлять отдельно и не заменять ими browser proof там, где риск именно layout/runtime;
- browser emulation не выдавать за проверку реального iOS/Android browser chrome, safe-area hardware или OS-level поведения;
- временный PR-trigger допустим только внутри конкретной разработки для RED/GREEN доказательства и должен быть удалён до merge.

Слой относится к `AFFECTED / FULL / QUALITY`: его запускают вручную после значимых responsive/navigation/layout изменений, перед крупным релизом или при воспроизведении UI-регрессии. Он не является обязательным gate каждого изменения.
